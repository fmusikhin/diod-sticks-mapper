# Requirements Document — `patch-core`

## Project Description (Input)
Спека `patch-core` — ядро патча Diod Sticks Mapper без TouchDesigner: модель патча, JSON-схема
(`schema_version`), адресация (выходы-«лумиверсы», Auto Span, пиксель не делится между юниверсами,
выравнивание 170/510, «порт с нового юниверса»), проверки конфликтов, импорт/экспорт CSV/JSON,
импорт пресетов Resolume Arena 7 (Advanced Output и Fixture Library; образцы — только синтетические,
без имён заказчиков), pytest без TouchDesigner. Ядро — чистый Python 3.12, стандартная библиотека, `src/core`.

## Introduction

`patch-core` — первая спека проекта и фундамент всех остальных: патч (JSON) — источник правды,
из него генерируются геометрия, адреса, карта DMX, листы для монтажников. Ядро живёт в `src/core`,
не знает про TouchDesigner и проверяется pytest. Все последующие спеки (`pixel-engine`, `patch-view`,
`mapping-editor`, `locate-test`, `fixture-editor`) читают и правят патч только через это ядро.

Источники: `README.md` («Модель данных патча», «Адресация и импорт», разбор Resolume),
`docs/architecture.md` §3, §5, §13 (факты этапа 0), `docs/resolume-analysis.md`, steering `.kiro/steering/*`.

В тексте ниже субъект требований — **patch-core** (ядро патча). Ключевые слова EARS оставлены
по-английски, остальное — по-русски.

### Термины

| Термин | Смысл |
|---|---|
| **Патч** | JSON-документ: холст, профили фикстур, фикстуры, выходы, группы |
| **Профиль** (`fixture_type`) | описание типа прибора: блоки каналов, порядок цвета, битность, раскладка, физика |
| **Фикстура** (`fixture`) | экземпляр профиля на холсте с направлением, адресом и группами |
| **Ячейка / пиксель** | один управляемый элемент фикстуры (у ленты — светодиод, у матрицы — клетка) |
| **Выход** (`output`) | аналог Lumiverse: протокол + цель (IP / broadcast / multicast) + стартовый юниверс + правила |
| **Порт** | необязательное деление выхода: цепочка фикстур, у которой свои правила старта и лимит пикселей |
| **Юниверс** | 512 каналов DMX; номер канала **с 1** (как в `DMX Map DAT` TD, подтверждено этапом 0) |
| **Port-address** | сквозной номер юниверса Art-Net 4 (0–32767) = `net·256 + subnet·16 + universe` |
| **Таблица адресов** | для каждой фикстуры и каждой ячейки: выход, юниверс, первый канал |
| **Таблица маршрутизации** | для каждого занятого юниверса: протокол, цель, priority |

## Boundary Context

- **In scope**: модель патча и её JSON-схема с версией; профили, фикстуры, выходы, порты, группы;
  авто- и ручная адресация с правилами выхода и порта; проверки конфликтов; таблицы адресов
  и маршрутизации; экспорт/импорт CSV и JSON; тесты pytest без TD; синтетические образцы.
- **Out of scope**: импорт пресетов Resolume Arena 7 (Advanced Output, Fixture Library) — отложен
  заказчиком в отдельную спеку (`resolume-import`), модель патча должна его допускать без ломки схемы;
  всё, что считается каждый кадр (выборка цвета, GLSL, POP, DMX-вывод) — `pixel-engine`;
  расчёт позиций ячеек на холсте (UV по длине дуги, кривые, дуги) — `pixel-engine` (решение заказчика);
  интерфейс (холст, карта DMX, инспектор) — `patch-view`, `mapping-editor`; редактор профиля — `fixture-editor`;
  режимы Locate — `locate-test` (ядро лишь хранит статус приёмки); лист патча для монтажников
  в HTML/MD — этап 2 (ядро отдаёт данные таблицами и CSV); 3D, цвет и мощность — этапы 2–3.
- **Adjacent expectations**:
  - `pixel-engine` строит геометрию по таблице адресов ядра и ставит на примитив `DMXFixtureUniverse`,
    `DMXFixtureChannel` (канал с 1), `DMXFixtureNetAddress` (uint32); правила «пиксель целиком
    в следующий юниверс, каналы 511–512 пустые» движок TD выполняет сам (этап 0) — таблица ядра
    обязана совпадать с этим поведением при правилах по умолчанию.
  - Ядро импортируется встроенным Python TouchDesigner без установки пакетов: только стандартная библиотека.
  - Пользовательские спеки (`patch-view`, `mapping-editor`, `locate-test`) правят патч только через
    публичные операции ядра и после каждой правки получают актуальные таблицы и список конфликтов.

## Requirements

### Requirement 1: Документ патча и JSON-схема

**Objective:** Как светохудожник, я хочу хранить патч одним JSON-файлом с версией схемы,
чтобы переносить его между проектами и версионировать в git без потерь.

#### Acceptance Criteria
1. The patch-core shall хранить патч как один JSON-документ с разделами `canvas`, `fixture_types`,
   `fixtures`, `outputs`, `groups` и целочисленным полем `schema_version`.
2. The patch-core shall присваивать каждому профилю, фикстуре, выходу, порту и группе уникальный
   строковый идентификатор, который не меняется при переадресации, перестановке и сохранении.
3. When патч сохраняется, the patch-core shall записывать JSON детерминированно (одинаковый патч →
   байт в байт одинаковый файл; стабильный порядок ключей, отступы, UTF-8 без BOM), чтобы diff в git
   показывал только смысловые изменения.
4. When патч загружается, the patch-core shall проверять документ по схеме и при нарушении сообщать
   путь к полю и причину (например, `fixtures[3].address.channel: 513 вне диапазона 1–512`).
5. If `schema_version` загружаемого файла старше текущей, the patch-core shall мигрировать документ
   к текущей версии и сообщить, что было изменено.
6. If `schema_version` загружаемого файла новее текущей, the patch-core shall отказать в загрузке
   с сообщением о требуемой версии и не портить файл.
7. If в документе встречаются неизвестные поля, the patch-core shall загрузить патч, сохранить эти поля
   без изменений при записи и вывести предупреждение (решение заказчика).
8. The patch-core shall создавать пустой патч с безопасными умолчаниями: холст 1280×720 px,
   выходов и фикстур нет, единицы — пиксели.
9. The patch-core shall хранить все пути (подложка холста и т. п.) относительно файла патча;
   абсолютные пути в документ не попадают.

### Requirement 2: Холст

**Objective:** Как пользователь, я хочу задать размер и единицы холста, чтобы фикстуры размещались
на картинке и на плане площадки одинаково.

#### Acceptance Criteria
1. The patch-core shall хранить размер холста в пикселях (ширина, высота) и единицы измерения
   координат фикстур: `px` или `m`.
2. Where единицы `m`, the patch-core shall хранить масштаб `px/м` и переводить координаты фикстур
   в пиксели холста при построении таблиц.
3. The patch-core shall хранить необязательную подложку холста (относительный путь к изображению)
   и не требовать её наличия при загрузке.

### Requirement 3: Профили фикстур

**Objective:** Как техник, я хочу описывать прибор один раз профилем, чтобы все его экземпляры
обновлялись при правке профиля и чтобы любой контроллер описывался данными.

#### Acceptance Criteria
1. The patch-core shall хранить у профиля: имя, тип (`strip` лента, `stick` стик, `matrix` матрица W×H,
   `bar` бар, `custom` своя таблица), число ячеек (или W×H), блоки каналов, физику, параметры цвета.
2. The patch-core shall описывать каналы профиля тремя блоками: общие каналы прибора (до ячеек),
   блок ячейки (повторяется на каждую ячейку), хвост (после ячеек); каждый блок — упорядоченный
   список каналов с именем, ролью и значением по умолчанию.
3. The patch-core shall задавать цветовые каналы ячейки строкой порядка из букв `R`, `G`, `B`, `W`, `A`
   (например `GRB`, `BWGR`, `RGBWA`) и допускать в блоке ячейки дополнительные нецветовые каналы
   (например диммер, строб, pan, tilt ячейки) — число каналов на ячейку произвольное.
4. The patch-core shall поддерживать битность цветовых каналов 8 или 16 бит на канал; при 16 бит
   каждый цветовой канал занимает два DMX-канала (старший, младший).
5. The patch-core shall вычислять для профиля число DMX-каналов на ячейку и общее число каналов прибора
   как `общие + ячейки × каналов_на_ячейку + хвост`.
6. Where тип `matrix`, the patch-core shall хранить раскладку ячеек одним из 16 вариантов
   (угол старта: 4 × направление первой линии: строки/столбцы × змейка: да/нет) и выдавать
   порядок ячеек в данных по этой раскладке.
7. Where тип `custom`, the patch-core shall хранить собственную таблицу ячеек (порядок в данных
   и относительная позиция каждой) произвольной длины.
8. The patch-core shall хранить физику профиля: шаг ячеек (мм), ячеек на метр, длину (мм) — любое
   из полей необязательно, но связанные поля согласованы (длина = шаг × (ячеек − 1) при заполнении).
9. The patch-core shall хранить параметры цвета профиля: гамма, баланс белого, режим выделения белого
   для `W`, ватт на ячейку — как данные, без вычислений в этой спеке.
10. When профиль изменён, the patch-core shall применять изменение ко всем фикстурам этого профиля
    и пересчитывать их число ячеек и каналов.
11. If профиль удаляется, пока на него ссылаются фикстуры, the patch-core shall отказать в удалении
    с перечислением фикстур.
12. The patch-core shall поставлять встроенные пресеты профилей: WS2811 (RGB), WS2812B (GRB),
    SK6812 (RGBW), TM1934 (RGB), стик 1 м 144 px, матрица 16×16, бар с общими каналами
    (конкретные значения — в design).

### Requirement 4: Фикстуры

**Objective:** Как пользователь, я хочу размещать экземпляры профилей на холсте с направлением,
сдвигом и исключениями, чтобы патч точно отражал монтаж.

#### Acceptance Criteria
1. The patch-core shall хранить у фикстуры: идентификатор, имя, профиль, список групп, форму входа,
   выборку, форму выхода (необязательно), направление, сдвиг, отключённые ячейки, «каждая N-я»,
   адрес, яркость, цвет, `mute`, статус приёмки.
2. The patch-core shall принимать форму входа одного из видов: `line` (две точки), `polyline`
   (точки), `curve` (опорные точки Безье), `arc` (центр, радиус, углы), `rect` (центр, размер, поворот)
   — и проверять, что у формы достаточно точек для своего вида.
   В этой спеке полностью поддерживаются (порядок ячеек, CSV) формы `line`, `polyline`, `rect`;
   `curve`, `arc` и таблица `custom` только принимаются и валидируются схемой (решение заказчика).
3. The patch-core shall хранить выборку цвета ячейки как данные: `point`, `area` (размер) или
   `elongated` (ширина вдоль/поперёк); расчёт самой выборки — `pixel-engine`.
4. The patch-core shall хранить направление сигнала (`forward` / `reverse`): при `reverse` первая
   ячейка данных лежит в конце формы.
5. The patch-core shall хранить два независимых сдвига (решение заказчика — нужны оба):
   `cell_offset` — на сколько ячеек начало данных смещено относительно начала формы, применяется
   к порядку ячеек по кругу; `channel_offset` — сколько DMX-каналов пропускается перед первым каналом
   фикстуры при автоадресации (пустые каналы остаются незанятыми и не отдаются другим фикстурам).
6. The patch-core shall хранить список отключённых ячеек (индексы) — такие ячейки сохраняют свой
   адрес, но помечаются в таблице адресов как отключённые.
7. Where задано «каждая N-я» (N ≥ 2), the patch-core shall помечать активной каждую N-ю ячейку
   начиная с первой, остальные — отключёнными; адреса всех ячеек сохраняются (решение заказчика).
8. Where профиль типа `strip` и у фикстуры задана длина, the patch-core shall вычислять число ячеек
   фикстуры из длины и шага профиля (округление вниз); иначе число ячеек берётся из профиля.
9. The patch-core shall хранить статус приёмки фикстуры из набора
   `none | ok | reversed | dead | misplaced | wrong_address`; применение «перевёрнута → исправить»
   (смена направления и сброс статуса) — одна операция ядра.
10. When фикстура дублируется (одиночно или группой), the patch-core shall создавать копии с новыми
    идентификаторами, тем же профилем и группами и смещением формы, заданным вызывающей стороной.
11. The patch-core shall хранить группы как именованные множества фикстур; фикстура может входить
    в несколько групп; вложенность групп не поддерживается в этой спеке.

### Requirement 5: Выходы и порты

**Objective:** Как техник, я хочу описать контроллер данными (протокол, цель, стартовый юниверс,
правила), чтобы движок не знал про железо, а смена контроллера сводилась к правке чисел.

#### Acceptance Criteria
1. The patch-core shall хранить у выхода: идентификатор, имя, протокол (`artnet` / `sacn`), цель,
   стартовый юниверс, число юниверсов (или «авто»), правила адресации, список портов (необязательно),
   частоту, ArtSync (Art-Net), priority (sACN, 0–200, по умолчанию 100), задержку в мс.
2. The patch-core shall принимать цель выхода одного из видов: unicast IP, broadcast (Art-Net),
   multicast (sACN, по умолчанию), и считать цель незаданной, если IP не указан. Цель одна на весь
   выход; другой IP — другой выход (решение заказчика, переопределения цели у отдельного юниверса нет).
3. While у выхода не задана цель, the patch-core shall подставлять в таблицу маршрутизации
   `127.0.0.1` (unicast) и помечать выход предупреждением «цель не задана».
4. Where протокол `artnet`, the patch-core shall хранить стартовый юниверс как port-address 0–32767
   и представлять его также в виде `net.subnet.universe` (net 0–127, subnet 0–15, universe 0–15);
   обе записи взаимно однозначны (пример этапа 0: 20 ↔ 0.1.4).
5. Where протокол `sacn`, the patch-core shall хранить юниверс как число 1–63999.
6. The patch-core shall хранить правила адресации выхода: `whole_pixel` (ячейка не делится между
   юниверсами; по умолчанию включено), `auto_span` (фикстура продолжается в следующем юниверсе;
   по умолчанию включено), `skip_511_512` (каналы 511–512 не используются; по умолчанию **выключено**).
   Юниверс заполняется полностью: ячеек в юниверсе = `floor(512 / каналов_на_ячейку)` при любом числе
   каналов на ячейку (3 → 170, 4 → 128, 7 → 73); фиксированного лимита «170 на юниверс» нет
   (решение заказчика).
7. Where у выхода заданы порты, the patch-core shall хранить у порта: номер, список фикстур в порядке
   цепочки, правило `new_universe` («порт с нового юниверса», по умолчанию включено), лимит ячеек
   на порт (необязательно), лимит юниверсов на порт (необязательно).
8. The patch-core shall допускать несколько выходов с одной целью (IP) при непересекающихся диапазонах
   юниверсов и несколько выходов с одинаковыми номерами юниверсов при разных целях (подтверждено этапом 0).
9. The patch-core shall поставлять пресеты чисел для проверки портов (ячеек на порт, юниверсов
   на порт) как данные без привязки к движку; состав пресетов — в design.

### Requirement 6: Автоадресация

**Objective:** Как пользователь, я хочу раздавать адреса автоматически по правилам выхода
и порта, чтобы 100 стиков × 144 px на 8 контроллерах патчились за минуты, а не вручную.

#### Acceptance Criteria
1. When запрошена автоадресация выхода, the patch-core shall раздать фикстурам выхода адреса
   последовательно в порядке фикстур (порядок портов, внутри порта — порядок цепочки; без портов —
   порядок списка фикстур выхода), начиная со стартового юниверса и канала 1.
2. The patch-core shall нумеровать каналы с 1 по 512 и юниверсы — по правилам протокола
   (port-address с 0 для Art-Net, с 1 для sACN).
3. While `whole_pixel` включено, when ячейке не хватает каналов до конца юниверса, the patch-core
   shall переносить ячейку целиком в следующий юниверс, оставляя остаток каналов пустым
   (пример: 200 ячеек RGB = 170 в первом юниверсе + 30 во втором; каналы 511–512 пустые).
4. While `auto_span` включено, the patch-core shall продолжать фикстуру, не поместившуюся в юниверс,
   в следующих юниверсах того же выхода без ограничения числа юниверсов на фикстуру.
5. If `auto_span` выключено и фикстура не помещается в юниверс, the patch-core shall не назначать
   адрес и выдать конфликт «фикстура не помещается в юниверс».
6. Where `skip_511_512` включено, the patch-core shall не использовать каналы 511–512 ни для
   одной ячейки (значимо для профилей с 1, 2, 4 каналами на ячейку, где ячейка иначе легла бы на 511–512).
7. The patch-core shall при правилах по умолчанию размещать в юниверсе `floor(512 / каналов_на_ячейку)`
   ячеек фикстуры с учётом общих каналов и `channel_offset` перед первой ячейкой, и продолжать
   следующую ячейку с канала 1 следующего юниверса.
8. While у порта включено `new_universe`, the patch-core shall начинать первую фикстуру порта
   с канала 1 первого свободного юниверса, даже если в предыдущем юниверсе остались каналы.
9. The patch-core shall начинать каждую следующую фикстуру с первого свободного канала после предыдущей
   (общие каналы профиля идут первыми), если правила порта не требуют нового юниверса;
   правила «каждая фикстура с нового юниверса» нет (решение заказчика).
10. If у фикстуры стоит ручной адрес (`manual`), the patch-core shall не трогать его при автоадресации
    и обходить занятые им каналы при раздаче остальным.
11. When группа фикстур дублируется с запросом адресов «следом», the patch-core shall раздать копиям
    адреса одним блоком, по порядку исходной группы, начиная с первого свободного канала после
    последней фикстуры выхода.
12. When запрошена раздача адресов подряд для выбранных фикстур (аналог Ctrl+D), the patch-core shall
    назначить им адреса последовательно от адреса первой выбранной фикстуры по правилам выхода.
13. The patch-core shall выполнять автоадресацию детерминированно: один и тот же патч и запрос →
    одинаковые адреса.
14. The patch-core shall завершать автоадресацию и проверки патча на 50 000 ячеек (350 фикстур
    по 144 px, 8 выходов) не дольше 1 с на рабочем ноутбуке, а на 20 000 ячеек — не дольше 0,3 с.

### Requirement 7: Проверки конфликтов

**Objective:** Как техник, я хочу видеть все конфликты адресов и ошибки настройки одним списком
с указанием фикстур, чтобы исправить их до выхода на площадку.

#### Acceptance Criteria
1. When патч проверяется, the patch-core shall возвращать список сообщений, у каждого: уровень
   (`error` / `warning`), код, текст по-русски, затронутые идентификаторы (фикстуры, выходы, порты),
   выход и юниверс (если применимо).
2. If два или более диапазона каналов пересекаются в одном юниверсе одной цели, the patch-core shall
   выдать `error` «пересечение каналов» с перечислением фикстур и общих каналов.
3. If ручной адрес выводит ячейку за канал 512 при выключенном `auto_span`, the patch-core shall
   выдать `error` «выход за 512».
4. If ручной адрес кладёт ячейку на границу юниверса при включённом `whole_pixel`, the patch-core shall
   выдать `error` «ячейка на границе юниверса» и указать, как движок перенесёт ячейку (в следующий юниверс).
5. If порт превышает лимит ячеек или юниверсов, the patch-core shall выдать `error` «лимит порта»
   с фактом и лимитом.
6. If два выхода с одной целью имеют пересекающиеся диапазоны юниверсов, the patch-core shall
   выдать `error` «дубль юниверса на одной цели».
7. If port-address Art-Net выходит за 32767 или юниверс sACN за 63999, the patch-core shall выдать
   `error` «юниверс вне диапазона протокола».
8. If фикстура ссылается на несуществующий профиль, выход, порт или группу, the patch-core shall
   выдать `error` «битая ссылка».
9. If у выхода не задана цель, the patch-core shall выдать `warning` «вывод на 127.0.0.1».
10. If фикстура без адреса (`unassigned`), the patch-core shall выдать `warning` «нет адреса».
11. If в одном выходе смешаны протоколы или у цели broadcast стоит sACN, the patch-core shall выдать `error`.
12. If форма фикстуры вырождена (линия нулевой длины, прямоугольник нулевого размера), the patch-core
    shall выдать `warning` «вырожденная форма»; патч при этом загружается.
13. The patch-core shall возвращать пустой список для патча без конфликтов и не блокировать сохранение
    патча с конфликтами (конфликты — свойство документа, а не отказ).

### Requirement 8: Таблицы адресов и маршрутизации

**Objective:** Как разработчик движка и как техник, я хочу получать из патча готовые таблицы,
чтобы движок ставил адреса на примитивы, а монтажник сверял юниверсы и каналы.

#### Acceptance Criteria
1. When запрошена таблица адресов, the patch-core shall выдать для каждой фикстуры: выход, протокол,
   стартовый юниверс (сквозной номер и `net.subnet.universe` для Art-Net), стартовый канал (с 1),
   число ячеек, число каналов, список занятых юниверсов с диапазонами каналов в каждом.
2. When запрошена таблица адресов по ячейкам, the patch-core shall выдать для каждой ячейки:
   фикстура, индекс ячейки в данных, юниверс, первый канал, число каналов, флаг «отключена».
3. The patch-core shall гарантировать, что таблица адресов при правилах по умолчанию совпадает
   с поведением движка TD, зафиксированным этапом 0: канал с 1, ячейка целиком в следующий юниверс,
   каналы 511–512 пустые для 3-канальных ячеек, юниверс 20 Art-Net = 0.1.4.
4. When запрошена таблица маршрутизации, the patch-core shall выдать для каждого занятого юниверса:
   выход, протокол, сквозной номер, цель (IP или multicast-группа), priority (sACN), задержку,
   частоту, ArtSync — по одной строке на юниверс, отсортированные по выходу и номеру.
5. The patch-core shall выдавать сводку патча: число фикстур, ячеек, каналов, юниверсов,
   выходов, конфликтов (`error` / `warning`).
6. The patch-core shall отдавать таблицы как структуры данных Python и как CSV (см. Requirement 9).

### Requirement 9: Экспорт и импорт CSV

**Objective:** Как пользователь, я хочу выгружать список фикстур в CSV и создавать фикстуры
из CSV (как в MADRIX и MadMapper), чтобы массово править патч в таблице и делать листы для монтажников.

#### Acceptance Criteria
1. When запрошен экспорт фикстур в CSV, the patch-core shall записать по строке на фикстуру
   с колонками: `id`, `name`, `fixture_type`, `groups`, `output`, `port`, `universe`, `channel`,
   `address_mode`, `cells`, `direction`, `shape`, `x1`, `y1`, `x2`, `y2` (для `line`), `points`
   (для прочих форм, строкой), `disabled`, `every_n`, `status`; разделитель `,`, кодировка UTF-8,
   заголовок обязателен, десятичный разделитель `.`.
2. When запрошен экспорт таблицы адресов, таблицы по ячейкам или таблицы маршрутизации в CSV,
   the patch-core shall записать их с заголовком, колонками как в Requirement 8.
3. When импортируется CSV фикстур, the patch-core shall создать фикстуры по строкам; обязательны
   колонки `name`, `fixture_type`, `shape` и координаты формы; остальные колонки необязательны
   и получают умолчания (адрес — `auto`, направление — `forward`).
4. If в строке CSV есть `id` существующей фикстуры, the patch-core shall обновить эту фикстуру,
   а не создавать новую.
5. If строка CSV ссылается на неизвестный профиль или выход, the patch-core shall пропустить строку,
   продолжить импорт и вернуть список ошибок с номерами строк.
6. The patch-core shall обеспечивать круговой обход: экспорт патча в CSV фикстур и импорт этого CSV
   в пустой патч с теми же профилями и выходами дают фикстуры с теми же адресами, формами и свойствами.
7. The patch-core shall принимать CSV с разделителем `;` и десятичной запятой (экспорт из русского Excel),
   определяя разделитель по заголовку.

### Requirement 10: Публичные операции ядра

**Objective:** Как разработчик следующих спек, я хочу править патч только через операции ядра,
чтобы интерфейс, движок и Locate не расходились с документом.

#### Acceptance Criteria
1. The patch-core shall предоставлять операции: создать пустой патч; загрузить / сохранить JSON;
   добавить / изменить / удалить профиль, фикстуру, выход, порт, группу; дублировать фикстуры
   и группы; назначить ручной адрес; автоадресовать выход или весь патч; раздать адреса подряд;
   проверить патч; получить таблицы и сводку; экспорт / импорт CSV;
   применить статус приёмки и «перевёрнута → исправить».
2. When выполняется любая операция правки, the patch-core shall оставлять патч валидным по схеме
   либо отказать в операции с сообщением, не изменяя патч.
3. The patch-core shall выполнять операции без побочных эффектов вне переданного патча (ни файлов,
   ни сети, ни глобального состояния), кроме явных «загрузить» и «сохранить».
4. The patch-core shall отдавать таблицы и конфликты как значения, пригодные для записи в DAT
   TouchDesigner без преобразования (списки строк одинаковой длины с заголовком).

### Requirement 11: Проверка и ограничения среды

**Objective:** Как заказчик, я хочу, чтобы ядро проверялось без TouchDesigner и работало
внутри него без установки пакетов, чтобы «готово» означало проверенный факт.

#### Acceptance Criteria
1. The patch-core shall использовать только стандартную библиотеку Python и не импортировать
   ничего из TouchDesigner и `src/td`.
2. The patch-core shall использовать только синтаксис и стандартную библиотеку Python 3.11
   (встроенный в TD 2025) и работать без изменений на системном 3.12 (решение заказчика).
3. The patch-core shall покрываться тестами pytest, запускаемыми командой `python -m pytest tests`
   вне TD, не дольше 30 с на рабочем ноутбуке.
4. The patch-core shall иметь тесты на каждое правило адресации (Requirement 6) с ожидаемыми
   таблицами, записанными вручную, включая случай этапа 0 (200 / 60 / 128 ячеек RGB на трёх целях,
   юниверс 20 Art-Net = 0.1.4).
5. The patch-core shall иметь тест кругового обхода JSON (загрузить → сохранить → загрузить →
   идентичный документ) и CSV (Requirement 9.6).
6. The patch-core shall поставлять примеры патчей в `examples/` (лента, стики, матрица, бар),
   загружаемые без конфликтов и с целью `127.0.0.1`.
7. The patch-core shall не содержать в коде, тестах и примерах реальных IP, названий площадок
   и данных заказчиков.
8. When спека считается выполненной, the patch-core shall иметь документацию публичных операций
   и формата JSON в `docs/`, актуальную на момент слияния.

## Решения заказчика (16.10.2026)

- Синтаксис Python 3.11. Геометрия ячеек — в `pixel-engine`. В этой спеке полностью — `line`/`polyline`/`rect`.
- Сдвиг — два поля: `cell_offset` (ячейки) и `channel_offset` (каналы).
- «Каждая N-я» — адреса у всех ячеек, светит каждая N-я.
- Юниверсы заполняются полностью при любом числе каналов на ячейку (цвет + pan/tilt и др.);
  `skip_511_512` по умолчанию выключено; лимита «170 на юниверс» нет.
- Правила «каждая фикстура с нового юниверса» нет.
- Импорт пресетов Resolume Arena — не в этой спеке, позже отдельной спекой.
- Цель (IP) одна на выход, другой IP = другой выход. Неизвестные поля JSON сохраняются при записи.
