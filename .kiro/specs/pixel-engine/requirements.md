# Requirements Document — `pixel-engine`

## Project Description (Input)
Спека `pixel-engine` — движок Diod Sticks Mapper внутри TouchDesigner: каркас компонента `dsm.tox`
(контракт компонента по `CONTRIBUTING.md` §4), построение POP-геометрии из патча через ядро `dsm_core`
(Python — только при правке патча), выборка цвета из входного TOP, пиксельная обработка на GPU,
DMX-вывод (один узел фикстур на профиль, один узел вывода на протокол, маршрутизация по юниверсам),
синхронизация с видео (частота = fps проекта, ArtSync, задержка на выход). Движок не знает про
конкретные контроллеры: контроллер — только данные патча.

## Introduction

`pixel-engine` — вторая спека проекта и первый код под TouchDesigner. Кто: VJ или светохудожник,
который вставляет `dsm.tox` в свой патч, подаёт на вход тот же TOP, что уходит на экраны, и указывает
файл патча. Сейчас: ядро `patch-core` умеет читать патч, раздавать адреса и отдавать таблицы сегментов
и маршрутизации, но ни один пиксель ещё не светится — нет компонента, геометрии, выборки цвета и вывода.
Что меняется: появляется компонент, который по патчу строит геометрию, каждый кадр без Python берёт
цвет из TOP и шлёт Art-Net / sACN на любое число контроллеров, байт в байт по таблице ядра
и синхронно с видео.

Источники: `README.md` («Конвейер кадра», «Синхронизация с видео», «Как вставить в патч», «Проверка»),
`docs/architecture.md` §2, §4, §6, §11–§14 (факты этапа 0 и грабли TD), `docs/core-api.md`
(контракт ядра: `segments_by_fixture`, `routing_table`, `cell_order`), `docs/patch-format.md`
(`sampling`, `direction`, `disabled`, `every_n`, `brightness`, `color`, `mute`, параметры выхода),
`CONTRIBUTING.md` §4–§6, steering `.kiro/steering/*`, спека `patch-core` (Adjacent expectations).

Субъект требований — **pixel-engine** (движок, он же компонент `dsm.tox`). Ключевые слова EARS
по-английски, остальное — по-русски.

### Термины

| Термин | Смысл |
|---|---|
| **Компонент** | `dsm.tox` — один COMP, который бросают в чужой патч; снаружи виден через пары и коннекторы |
| **Патч** | JSON-документ ядра `dsm_core`, источник правды (профили, фикстуры, выходы, группы) |
| **Ядро** | пакет `dsm_core` (`patch-core`): читает патч, раздаёт адреса, отдаёт таблицы |
| **Ячейка / пиксель** | один управляемый элемент фикстуры; у ячейки есть индекс в данных (`data_index`) |
| **Сегмент** | кусок фикстуры внутри одного юниверса: `universe`, `first_channel`, `last_channel`, `kind` (head / cells / tail), `first_cell`, `n_cells` — отдаёт ядро |
| **Геометрия** | набор точек и примитивов, по которому считается цвет и адрес; строится из патча |
| **Выборка** | как берётся цвет ячейки с картинки: точка, область, вытянутая область |
| **Выход** | аналог Lumiverse: протокол, цель (IP / broadcast / multicast), юниверсы, частота, ArtSync, priority, задержка |
| **Таблица маршрутизации** | строка на занятый юниверс: протокол, цель, priority, задержка, частота — отдаёт ядро |
| **Кадр** | один кук проекта-хозяина; «каждый кадр» = в каждом куке без Python |
| **Карта DMX** | таблица «юниверс → канал → ячейка / фикстура», которую движок показывает по своей геометрии |

## Boundary Context

- **In scope**: компонент `dsm.tox` и его публичный контракт (страница `Info`, пары, вход TOP,
  выходы, DAT колбэков); загрузка патча через ядро и пересборка геометрии при правке; геометрия
  для форм `line`, `polyline`, `rect` (включая матрицы W×H с 16 раскладками); выборка цвета точкой;
  пиксельная обработка: мастер, яркость / цвет / mute фикстуры, порядок цветовых каналов, 8 и 16 бит,
  значения по умолчанию для нецветовых каналов; DMX-вывод Art-Net и sACN по таблице маршрутизации
  ядра, независимо от числа контроллеров; синхронизация с видео (частота, ArtSync, задержка на выход,
  повтор кадра); диагностика (превью, карта DMX, счётчики); проверка на стенде: байт в байт, стоимость кадра.
- **Out of scope**: любой интерфейс (холст, инспектор, карта DMX как экран) — `patch-view`, `mapping-editor`;
  режимы Locate и тест-паттерны — `locate-test` (движок лишь оставляет точку подключения, см. ниже);
  Палитра и генераторы — `palette-generators`; темп — `beat-sync`; гамма, баланс белого, RGB→RGBW,
  лимит мощности — `color-power` (этап 3; значения из патча читаются, но не применяются);
  формы `curve`, `arc`, `custom` и выборка «область» / «вытянутая область» — этап 2 (решение заказчика);
  3D — `space-3d`; правка патча (любая операция, меняющая JSON) — движок патч только читает;
  пресеты и особенности конкретных контроллеров.
- **Adjacent expectations**:
  - Ядро `dsm_core` — единственный источник адресов: движок берёт `segments_by_fixture`,
    `routing_table`, `cell_order` и не считает адреса сам; ядро импортируется встроенным Python TD
    без установки пакетов.
  - Правила «ячейка целиком в следующий юниверс, каналы 511–512 пустые» движок TD выполняет сам
    (этап 0), поэтому сегменты ядра при правилах по умолчанию совпадают с тем, что уйдёт в сеть.
  - `locate-test` и `palette-generators` подключаются к движку между выборкой цвета и выводом
    (цвет ячейки можно заменить или смешать), не меняя геометрию и адреса.
  - Интерфейсные спеки меняют патч через ядро и зовут у движка перезагрузку; движок сам файл не правит.

## Requirements

### Requirement 1: Компонент и его контракт

**Objective:** Как VJ, я хочу бросить `dsm.tox` в любой патч и подключить его за минуту,
чтобы маппер работал в чужом проекте без правок и в нескольких копиях.

#### Acceptance Criteria
1. The pixel-engine shall поставляться одним компонентом `dsm.tox` с одним входом TOP (картинка)
   и публичным контрактом только через кастом-пары, коннекторы и DAT колбэков.
2. The pixel-engine shall иметь на странице `Info` пары `Id = dsm/mapper` и `Version = MAJOR.MINOR`
   (обе `readOnly`), причём `float(par.Version)` работает; `Version` этой спеки — `0.1`.
3. The pixel-engine shall иметь пары: файл патча, перезагрузка патча, автоперезагрузка, `Active`,
   `Master` (0–1), локальный адрес (сетевая карта), предподготовка входа (требование 4); частота,
   ArtSync и задержка задаются в патче на каждый выход, пар компонента для них нет (решение заказчика);
   названия пар — с заглавной, одним словом.
4. The pixel-engine shall иметь выходы: превью TOP (картинка с ячейками поверх входа), пиксели
   как TOP (цвет каждой ячейки после обработки) и как CHOP, информация (счётчики из требования 9)
   и DAT карты DMX.
5. The pixel-engine shall иметь DAT колбэков как минимум с `onPatchLoaded(patch, issues)`
   и `onOutputError(message)`; механика настраивается парами, политика — колбэками.
6. The pixel-engine shall не содержать абсолютных путей и глобальных OP-шорткатов: все ссылки
   относительные или через `parentshortcut`; путь к файлу патча хранится как задан пользователем,
   относительный путь считается от файла проекта-хозяина.
7. When в один проект вставлены две и более копии компонента, the pixel-engine shall работать
   в каждой копии независимо (свой патч, своя геометрия, свой вывод), без конфликтов имён.
8. The pixel-engine shall экспортироваться пустой заготовкой: без загруженного патча, без контента,
   без накопленного состояния; внутри — DAT `agents_md` с описанием контракта. `Version` первой
   версии — `0.1`, `1.00` — на релизе MVP.
9. The pixel-engine shall работать в TD 2025.33070 Non-Commercial и не зависеть от размера входного
   TOP: вход любого разрешения принимается, ограничения лицензии (TOP ≤ 1280×1280) на движок не влияют.
10. The pixel-engine shall держать исходники слоя TD текстом в репозитории (`src/td`, `src/glsl`)
    и синхронизировать их с DAT компонента; текст — источник правды.

### Requirement 2: Загрузка патча и перезагрузка

**Objective:** Как светохудожник, я хочу указать файл патча и видеть, что он принят или почему нет,
чтобы ошибка адресации не ушла молча на площадку.

#### Acceptance Criteria
1. When задан файл патча или нажата перезагрузка, the pixel-engine shall загрузить патч через ядро,
   выполнить автоадресацию по правилам ядра для фикстур в режиме `auto`, получить сегменты
   и таблицу маршрутизации и пересобрать геометрию.
2. When патч загружен, the pixel-engine shall вызвать `onPatchLoaded` с патчем и списком конфликтов
   ядра и показать в информации число фикстур, ячеек, юниверсов, ошибок и предупреждений.
3. If файл не найден, не читается или не проходит схему ядра, the pixel-engine shall оставить
   предыдущую геометрию и вывод без изменений, показать текст ошибки ядра (с путём к полю)
   и вызвать `onOutputError`.
4. If ядро вернуло конфликты уровня «ошибка» (`channel_overlap`, `over_512`, `fixture_too_long`,
   `port_limit`, `universe_dup`, `universe_range`, `broken_ref`, `protocol_mismatch`),
   the pixel-engine shall загрузить патч, не выводить только фикстуры, которых касаются ошибки,
   держать вывод остальных и перечислить проблемные в информации (решение заказчика).
5. If ядро вернуло только предупреждения (`target_missing`, `unassigned`, `degenerate_shape`,
   `stale_auto`, `cell_on_boundary`), the pixel-engine shall вывести патч целиком и показать
   предупреждения в информации; фикстуры без адреса (`unassigned`) в вывод не попадают.
6. The pixel-engine shall не изменять файл патча и не записывать его: движок патч только читает.
7. While включена автоперезагрузка (пара, по умолчанию включена), when файл патча изменён
   на диске, the pixel-engine shall перезагрузить его автоматически и сообщить в информации.
8. While патч не задан или не загружен, the pixel-engine shall ничего не отправлять в сеть,
   показывать пустую геометрию и статус «патч не загружен».

### Requirement 3: Геометрия из патча

**Objective:** Как разработчик, я хочу, чтобы геометрия строилась из патча один раз и совпадала
с таблицами ядра, чтобы каждый кадр оставался без Python, а адреса совпадали с листом монтажника.

#### Acceptance Criteria
1. When патч загружен, the pixel-engine shall построить геометрию, где один примитив = один сегмент
   ядра, а точки примитива = ячейки сегмента в порядке `data_index` от `first_cell`
   (не point-примитив на ячейку).
2. The pixel-engine shall поставить на каждый примитив адрес сегмента атрибутами класса primitive
   типа uint32: юниверс (`universe` ядра), первый канал (`first_channel`, канал с 1) и сетевой адрес
   (IP цели из таблицы маршрутизации) — ровно в тех именах, которые понимает узел фикстур TD.
3. The pixel-engine shall хранить у каждой точки: UV на картинке (0–1), позицию на холсте
   в пикселях, индекс ячейки в данных, индекс фикстуры и признак активности.
4. Where форма фикстуры `line`, `polyline` или `rect`, the pixel-engine shall располагать ячейки
   равномерно по длине дуги формы: центр ячейки `i` на расстоянии `(i + 0,5) / n` длины от начала,
   с учётом `direction` и `cell_offset` ядра.
5. Where профиль типа `matrix` на форме `rect`, the pixel-engine shall располагать ячейки в клетках
   сетки W×H прямоугольника (с поворотом `rotation_deg`), а порядок данных брать из `cell_order` ядра
   по одной из 16 раскладок.
5a. Where профиль типа `matrix` на форме `line` или `polyline`, the pixel-engine shall класть ячейки
   по длине формы как ленту, в порядке данных `cell_order` (решение заказчика).
6. Where у холста единицы `m`, the pixel-engine shall переводить координаты фикстур в пиксели холста
   через `px_per_m` до расчёта UV.
7. Where у фикстуры отключённые ячейки (`disabled`) или шаг `every_n`, the pixel-engine shall оставить
   этим ячейкам адрес и место в данных, но выводить для них значения по умолчанию (цвет — ноль);
   признак активности у них — ложь.
8. If форма фикстуры `curve`, `arc` или `custom`, the pixel-engine shall не строить для неё геометрию,
   не выводить её и сообщить в информации «форма не поддерживается в этой версии».
9. The pixel-engine shall выполнять Python только при загрузке и перезагрузке патча; в куке кадра
   Python не исполняется (проверяется профилировщиком TD: ни одного Python-кука за 120 кадров
   при неизменном патче).
10. When патч из 100 фикстур по 144 ячейки (14 400 ячеек) загружен, the pixel-engine shall построить
    геометрию не дольше 1 с; при 50 000 ячеек — не дольше 3 с.
11. The pixel-engine shall предоставлять DAT карты DMX: для каждого сегмента — фикстура, юниверс,
    первый и последний канал, вид сегмента, первая ячейка, число ячеек — в тех же колонках,
    что `segment_table` ядра, чтобы сверять их построчно.

### Requirement 4: Вход и выборка цвета

**Objective:** Как VJ, я хочу, чтобы на пиксели шёл тот же кадр, что на экраны,
чтобы LED не отставал и не мерцал.

#### Acceptance Criteria
1. The pixel-engine shall брать картинку с единственного входа TOP в том же куке, без NDI,
   без второго процесса и без копии через CPU.
2. The pixel-engine shall иметь предподготовку входа парами компонента: кроп (прямоугольник
   в долях 0–1), ограничение разрешения (максимальная сторона, по умолчанию — без ограничения),
   уровни (чёрная и белая точки, гамма входа); по умолчанию предподготовка нейтральна и картинка
   проходит как есть (решение заказчика).
2a. The pixel-engine shall считать UV ячеек относительно холста патча и растягивать холст
   на подготовленную картинку целиком: холст `w×h` соответствует всей картинке после кропа
   независимо от её разрешения.
3. Where выборка фикстуры `point`, the pixel-engine shall брать цвет ячейки одним отсчётом
   в центре ячейки с билинейной фильтрацией.
4. Where выборка фикстуры `area` или `elongated`, the pixel-engine shall в этой версии брать цвет
   как для `point` и один раз при загрузке патча предупредить в информации «выборка по области —
   этап 2» (решение заказчика).
5. If ячейка выходит за границы картинки (UV вне 0–1), the pixel-engine shall выдать для неё чёрный.
6. If вход не подключён, the pixel-engine shall считать картинку чёрной и продолжать вывод
   (нули в каналы), а в информации показать «нет входа».
7. The pixel-engine shall работать с входом любого формата TOP (8 бит, 16 бит, float) и брать цвет
   в линейном диапазоне 0–1 без преобразования цветового пространства (гамма — спека `color-power`).

### Requirement 5: Пиксельная обработка

**Objective:** Как техник, я хочу, чтобы профиль из патча (порядок цвета, битность, служебные каналы)
и свойства фикстуры (яркость, цвет, mute) применялись сами, чтобы любой прибор описывался данными.

#### Acceptance Criteria
1. The pixel-engine shall умножать цвет каждой ячейки на `Master` компонента, на `brightness`
   фикстуры и на её `color` (поканально); при `mute` фикстуры — на ноль.
2. The pixel-engine shall раскладывать цвет ячейки в DMX-каналы по строке `color_order` профиля
   (`R`, `G`, `B`, `W`, `A`); канал `W` и `A` в этой версии — ноль, если нет своего значения
   (режимы белого — `color-power`).
3. Where `bits = 16`, the pixel-engine shall писать каждый цветовой канал в два DMX-канала
   (старший, младший) из 16-битного значения `round(v × 65535)`.
4. Where в профиле есть блоки `head`, `tail` или `cell_extra`, the pixel-engine shall выводить
   в эти каналы их `default` из профиля; длина и порядок каналов совпадают с ядром.
5. The pixel-engine shall переводить значение 0–1 в байт так, чтобы перехват байт в байт совпадал
   с ожидаемой таблицей стенда (правило квантования фиксируется в design и в тесте стенда).
6. The pixel-engine shall обеспечить точку подключения между выборкой и выводом, куда `locate-test`
   и `palette-generators` подменяют цвет ячеек по индексу фикстуры, не меняя геометрию и адреса.
7. The pixel-engine shall выполнять всю обработку на GPU; при изменении `Master`, `Active`
   и свойств фикстур из патча геометрия не пересобирается.

### Requirement 6: DMX-вывод и маршрутизация

**Objective:** Как техник, я хочу, чтобы любое число контроллеров и фикстур выводилось одной схемой,
чтобы смена железа была правкой патча, а не движка.

#### Acceptance Criteria
1. The pixel-engine shall выводить все фикстуры через один узел фикстур на профиль и один узел вывода
   на протокол (Art-Net, sACN); число узлов не зависит от числа фикстур, выходов и контроллеров.
2. The pixel-engine shall адресовать пакеты по таблице маршрутизации ядра: для каждого юниверса —
   цель (unicast IP, broadcast, multicast sACN `239.255.hi.lo`), протокол и priority sACN.
3. The pixel-engine shall передавать номер юниверса ядра без изменений: Art-Net — как port-address
   (`net·256 + subnet·16 + universe`, 20 = 0.1.4), sACN — как сквозной номер 1–63999.
4. If у выхода не задан IP (`target_missing`), the pixel-engine shall слать его юниверсы
   на 127.0.0.1 и показывать предупреждение (безопасное умолчание).
5. The pixel-engine shall не содержать веток, параметров и размеров под конкретный контроллер;
   любая особенность железа выражается данными патча (стартовый юниверс, правила выхода, частота, ArtSync).
6. While `Active` выключен, the pixel-engine shall не отправлять пакеты и продолжать считать превью.
7. When `Active` включён и патч загружен, the pixel-engine shall отправлять пакеты каждый кадр сам,
   без Python и без открытого окна компонента (viewer выключен).
8. If цель недоступна (адаптер без линка, хост не отвечает), the pixel-engine shall продолжать
   работу без падения частоты кадров и без ошибок операторов; факт отсутствия линка — в информации,
   если TD его сообщает.
9. Where задан локальный адрес (сетевая карта), the pixel-engine shall отправлять все пакеты
   с этого интерфейса; по умолчанию — с системного.
10. When на стенде `examples/sticks_8x_artnet.json` (и остальные примеры из `examples/`) загружены
    при цели 127.0.0.1, the pixel-engine shall дать перехват `tools/dmx_listen.py`, совпадающий
    байт в байт с таблицей ядра для всех юниверсов обоих протоколов (включая пустые каналы 511–512).

### Requirement 7: Синхронизация с видео

**Objective:** Как VJ, я хочу, чтобы LED совпадал с экраном по кадру,
чтобы один контент на видео и пикселях не расходился.

#### Acceptance Criteria
1. The pixel-engine shall отправлять кадр DMX в том же куке, в котором получен кадр входа:
   задержка между входом и выходом в сеть не больше 1 кадра проекта.
2. The pixel-engine shall выводить с частотой проекта (fps хозяина) и показывать фактическую
   частоту пакетов на юниверс в информации; делитель частоты в этой версии не нужен (решение заказчика).
3. The pixel-engine shall брать частоту (`rate_hz`), ArtSync (`art_sync`) и задержку (`delay_ms`)
   из патча на каждый выход; пар компонента, переопределяющих их, нет (решение заказчика).
4. Where у выхода в патче `art_sync = true`, the pixel-engine shall слать пакет ArtSync после пакетов
   каждого кадра для юниверсов этого выхода.
5. Where у выхода задана `delay_ms`, the pixel-engine shall задерживать его юниверсы на это время
   (с точностью до кадра), чтобы LED совпадал с экраном или проектором (решение заказчика: в этой спеке).
6. If кадр входа не обновился (вход не кукнулся), the pixel-engine shall повторить последние
   значения, не пропуская отправку.
7. The pixel-engine shall не терять кадры при `realTime = False` (рендер в файл): пакеты идут
   на каждый кук.

### Requirement 8: Производительность

**Objective:** Как VJ, я хочу, чтобы маппер не съедал бюджет кадра шоу,
чтобы 60 fps держались и с 20 тысячами пикселей.

#### Acceptance Criteria
1. The pixel-engine shall стоить не больше 1 мс на кадр (CPU + GPU суммарно по узлам компонента)
   при 20 000 ячеек, 60 fps, цепочка кукается каждый кадр — критерий MVP.
2. The pixel-engine shall при 50 000 ячеек укладываться в 3,5 мс на кадр (этап 0: 2,6–2,9 мс GPU
   на узле фикстур при line strip на фикстуру).
3. The pixel-engine shall не создавать за кадр ни одного Python-кука, ни одного CPU-копирования
   текстуры и ни одной перестройки геометрии при неизменном патче.
4. The pixel-engine shall замерять стоимость кадра скриптом стенда (как в `test_stage0`) и держать
   результат в документации при каждом изменении конвейера.

### Requirement 9: Диагностика

**Objective:** Как техник, я хочу видеть, что движок шлёт и куда,
чтобы искать проблему на площадке по фактам, а не по памяти.

#### Acceptance Criteria
1. The pixel-engine shall показывать в информации: число фикстур, ячеек, юниверсов, выходов;
   fps проекта; частоту пакетов; ошибки и предупреждения ядра; состояние патча
   (загружен / ошибка / не задан); состояние входа.
2. The pixel-engine shall давать превью TOP: вход с наложенными ячейками (точки цветом вывода)
   и стрелкой направления у каждой фикстуры; превью не влияет на вывод и стоит не дороже 0,5 мс.
3. The pixel-engine shall давать DAT карты DMX по требованию 3.11 и DAT маршрутизации
   (колонки `routing_table` ядра).
3a. The pixel-engine shall давать пиксели как TOP (одна строка или сетка: ячейка = пиксель, цвет после
   обработки, порядок — фикстуры по патчу, внутри — `data_index`) и как CHOP (каналы `r`, `g`, `b`
   по тем же индексам), без Python в кадре (решение заказчика: в этой спеке).
4. When произошла ошибка вывода или загрузки, the pixel-engine shall вызвать `onOutputError`
   с текстом по-русски и показать его в информации до следующей успешной загрузки.
5. The pixel-engine shall не писать в textport каждый кадр; сообщения — только при событиях.

### Requirement 10: Проверка и приёмка

**Objective:** Как заказчик, я хочу принимать спеку по фактам,
чтобы «готово» означало проверенный вывод.

#### Acceptance Criteria
1. The pixel-engine shall иметь стенд в `td/dsm_dev.toe`, где компонент загружает каждый пример
   из `examples/` и перехват `tools/dmx_listen.py` на 127.0.0.x сравнивается с `segment_table`
   и `cell_table` ядра байт в байт — автоматически, скриптом, с отчётом «совпало / расхождения».
2. The pixel-engine shall иметь сверку DAT карты DMX с таблицей ядра построчно для каждого примера.
3. The pixel-engine shall иметь замер стоимости кадра на 20 000 и 50 000 ячеек с таблицей в
   `docs/architecture.md`.
4. The pixel-engine shall пройти дым-тест `.tox` из `CONTRIBUTING.md` §5: пустой COMP нового проекта,
   `Id` и `Version`, нет `errors()` и `scriptErrors()`, пример патча шлёт ожидаемое на 127.0.0.1.
5. The pixel-engine shall иметь pytest-тесты для той части слоя TD, что не зависит от TD
   (расчёт UV по длине дуги, раскладка ячеек прямоугольника, подготовка массивов атрибутов).
6. The pixel-engine shall обновить документацию: `docs/architecture.md` §4 и §6 по факту,
   новый `docs/engine.md` (контракт компонента: пары, выходы, колбэки, точка подключения),
   `README.md` (таблица спек), `CHANGELOG.md`.
7. The pixel-engine shall обновить плейбук проекта (`docs/architecture.md` §14) новыми граблями TD,
   найденными при реализации, сразу по факту.
